# Device Management

Authentication does not happen in isolation from the device or client environment in which it takes place.

A user may authenticate from a desktop browser, a mobile application, or several different environments simultaneously. Each environment can have its own authentication state, activity history, and security requirements.

UltimateAuth supports **device-aware session management** by associating authentication sessions with device context and organizing related sessions through `SessionChain`.

This provides a foundation for device-level visibility, session continuity, and targeted security operations without treating device identity as a substitute for user authentication.

## Understanding Device-Aware Authentication

Traditional token-based authentication can be implemented without explicitly modeling the client environment.

A token is issued, validated, and eventually expires or is revoked.

That approach is sufficient for some applications, but it becomes limiting when an application needs to distinguish between different client environments belonging to the same user.

For example:

- A user signs in from both a desktop browser and a mobile application.
- An administrator needs to revoke sessions associated with one client environment.
- A session is refreshed repeatedly while remaining associated with the same device context.
- An application needs to apply session limits or track activity across client environments.

UltimateAuth separates these concerns through its session and chain model.

The objective is not to prove the physical identity of a device. It is to provide a structured way to associate authentication activity with a recognizable client context.

## Device Context and SessionChain

The central concept in UltimateAuth's device-aware model is `SessionChain`.

A session represents authentication state.

A `SessionChain` groups related session activity under a persistent chain identity, which can be associated with a device or client environment.

Conceptually:

```text
User Identity
    |
    +-- SessionChain (Desktop Browser)
    |       |
    |       +-- Session
    |       +-- Session / Rotation History
    |
    +-- SessionChain (Mobile Application)
            |
            +-- Session
            +-- Session / Rotation History
```

This diagram illustrates the relationship between identity, chain, and session. It does not imply that every authentication mode retains multiple simultaneous session records or stores a complete rotation history.

### A Chain Is Not a Physical Device

A `SessionChain` should not be understood as a physical hardware identifier.

It represents a logical continuity boundary for related authentication sessions.

A single physical device may use different browsers, application installations, or isolated client storage environments.

Conversely, device identifiers supplied by clients are not necessarily reliable proof that requests originate from the same physical device.

The practical relationship is:

**A device context can be associated with a SessionChain, but the chain itself is an authentication-session concept.**

This distinction is important when designing security rules around device recognition and session revocation.

## Device Information

Device-aware session management can use information describing the client environment.

Relevant information may include:

| Information | Purpose |
|---|---|
| `DeviceId` | Identifies a client-reported or application-managed device context |
| Platform | Distinguishes environments such as web and mobile |
| Operating system | Provides client environment metadata |
| Browser | Describes the browser environment when applicable |
| IP address | Provides network context for security and activity analysis |

The availability and reliability of this information depend on the client platform and the application's integration.

Not every client can provide the same metadata.

### DeviceId and Trust

A `DeviceId` is useful for identifying a client environment across requests or authentication operations.

However, an identifier alone is not proof of device ownership.

A value stored in browser storage, for example, may be copied, cleared, or replaced. An identifier generated by a mobile application may change after application data is removed.

For that reason, device recognition must not be confused with authentication.

UltimateAuth's authentication and session validation rules remain responsible for determining whether a request is authorized to use the associated authentication state.

### Device Fingerprinting

Platform, operating system, browser, and network information may help describe a client environment.

These attributes are not inherently unique or stable.

Multiple devices can share similar attributes, and a single device can present different attributes over time.

They should therefore be treated as contextual signals rather than a guaranteed device fingerprint.

Applications requiring stronger device assurance need an appropriate proof or binding mechanism in addition to ordinary metadata.

## Device Continuity

Device continuity describes how authentication activity remains associated with an existing client context.

A session chain provides the logical structure for maintaining that continuity.

### First Authentication

When an authentication flow establishes a new session, the session infrastructure determines the appropriate chain association.

If a new chain is required, the session is associated with that chain.

The resulting chain can represent the beginning of a device-associated authentication history.

### Subsequent Authentication

A later authentication from the same client environment may be associated with an existing chain when the configured matching and security conditions permit it.

However, recognizing a device identifier does not automatically require the system to reuse a previous chain.

Chain association must respect the applicable lifecycle, validity, and security rules.

For example, a revoked chain should not become trusted again merely because a client presents the same device identifier.

### Device Continuity Is Not Session Continuity

A client environment can remain recognizable even when its previous authentication session has expired.

Likewise, a new authentication session can be established without inheriting the validity of an earlier session.

The chain model allows related activity to be organized while keeping session validity subject to authentication and security rules.

## Activity Tracking

Device-associated session management can maintain information about authentication activity.

Examples include:

- When a chain was created.
- When related authentication activity was last observed.
- How often relevant session activity was recorded.
- How many rotation operations were associated with the chain.

Fields such as `LastSeenAt`, `TouchCount`, and `RotationCount` help describe these aspects of the session lifecycle.

### Touch Operations

A touch operation records qualifying session activity according to the configured session behavior.

Depending on the authentication mode and session strategy, this may update activity metadata such as the last-seen timestamp or touch counter.

Touch behavior should not be interpreted as a guarantee that every authenticated HTTP request updates persistent device activity.

Different authentication modes have different requirements for consulting and updating server-side session state.

### Rotation Tracking

Token or session rotation may replace authentication material while preserving the logical relationship with an existing chain.

Where rotation tracking is supported, the chain can maintain information about those transitions.

This makes it possible to distinguish the continuity of a client environment from the lifecycle of an individual credential or session.

Rotation counts are operational signals. They do not independently establish that a device is legitimate or that suspicious activity has occurred.

## Logout and Device Revocation

Logout and chain revocation address different security scopes.

### Logout

Logout terminates the authentication state targeted by the logout operation.

Its precise effect depends on the authentication mode, the credentials involved, and the configured session behavior.

A logout operation does not necessarily mean that every session associated with the same device context has been revoked.

It also does not necessarily require deleting the associated chain record.

### Chain Revocation

Chain revocation targets the logical group of sessions associated with a chain.

It provides a broader security operation than terminating a single session.

This is useful when an application needs to invalidate the authentication continuity associated with a particular client environment.

For example, if a user believes a mobile application session has been compromised, the application may revoke the corresponding chain rather than revoking unrelated sessions associated with other environments.

### Revocation Does Not Establish Device Trust

A retained chain record is not equivalent to a trusted device.

Likewise, removing or revoking a chain does not physically block a device from attempting to authenticate again.

Whether a new authentication attempt is permitted depends on the authentication flow and the applicable security policies.

The chain model provides a boundary for managing authentication state; it is not a permanent device allowlist or hardware security mechanism.

## Device Binding and Security Boundaries

Device-aware authentication can associate session state with device context.

However, the strength of that association depends on what is actually validated.

There is an important distinction between:

- **Device metadata:** Information describing a client environment.
- **Device identification:** An identifier used to recognize a client context.
- **Device binding:** A security requirement connecting authentication material to a validated device-related condition.
- **Device authentication:** Proof that a client possesses an appropriate device-bound secret or cryptographic key.

These concepts provide different levels of assurance.

An application must not assume that supplying a `DeviceId` alone prevents stolen credentials from being reused elsewhere.

Security guarantees depend on the binding and validation mechanisms enforced by the configured authentication infrastructure.

## Device Management Across Authentication Modes

UltimateAuth supports different authentication modes, and device-aware session behavior must be understood within those modes.

| Mode | Device and session considerations |
|---|---|
| **PureOpaque** | Server-side session state is authoritative for protected requests, allowing session validity to be evaluated against server-managed state. |
| **Hybrid** | Opaque access and refresh credentials are associated with server-authoritative session state. |
| **SemiHybrid** | Server-side session state participates in lifecycle operations, while issued JWT access tokens may remain valid until expiration. |
| **PureJwt** | Protected requests are primarily validated from JWT contents; server-side device and session enforcement depends on the configured supporting infrastructure. |

The presence of a device-associated chain does not imply identical enforcement behavior in every mode.

### Revocation and JWT Validity

In modes that validate protected requests against authoritative server-side session state, session revocation can affect subsequent requests through that validation.

In JWT-based modes, a previously issued access token may remain valid until expiration if protected requests do not consult current revocation state.

Therefore, revoking a device-associated chain must not be described as universally invalidating every previously issued access token immediately.

See [Authentication Modes](/docs/fundamentals/authentication-modes).

## Session and Device Limits

Applications may need to limit how many authentication sessions or client environments a user can maintain.

UltimateAuth's session configuration provides the architectural place for managing supported session and chain constraints.

Depending on the configured capabilities, these constraints may concern:

- The number of chains associated with a user.
- The number of sessions associated with a chain.
- Session expiration and activity behavior.
- The treatment of device context changes.
- Revocation and lifecycle rules.

The exact available options and enforcement behavior depend on the authentication mode and session configuration.

Device management should not be understood as a separate enforcement system operating independently of session management.

## Operational Visibility

Device-associated session information can help applications present useful security information to users or administrators.

For example, an account management interface may display recognizable client environments and provide an option to revoke related sessions.

Such interfaces should distinguish between recorded information and verified facts.

A browser name or IP address may help a user recognize an activity record, but it does not conclusively identify the person or physical device involved.

Likewise, activity counters can support monitoring without independently providing anomaly detection.

UltimateAuth provides session and chain concepts that applications can use for these experiences, while the application's security and user-interface requirements determine how the information should be presented.

## Architectural Perspective

Device management in UltimateAuth is built on the relationship between identity, session, and chain.

**The user identity identifies the account. The session represents authentication state. The SessionChain organizes related session continuity, potentially associated with a device context.**

This model enables targeted session management and device-aware security operations without making device metadata an independent source of authentication trust.

It also preserves an important architectural boundary: device recognition, session validity, and authorization remain distinct security concerns.
