# Migrating to v0.2.0

**Migration Impact: High — In Progress**

**Latest published prerelease reviewed: v0.2.0-preview.4**

This guide covers migration requirements for the upcoming UltimateAuth v0.2.0 release.

The guide is provisional and will be updated as new preview and release candidate versions become available. The final migration requirements may change before the stable v0.2.0 release.

## Migration Overview

UltimateAuth v0.2.0 introduces new authentication capabilities, strengthens security defaults, and reorganizes several public configuration APIs.

For applications using the built-in integrations and default authentication behavior, migration primarily involves reviewing configuration changes, providing production cryptographic keys, and applying any required database migrations.

Applications with custom authentication policies, persistence stores, credential delivery settings, or Resource API configurations should also review the detailed sections below.

**Recommended upgrade sequence:**

1. Update renamed public APIs and configuration properties.
2. Configure and validate cryptographic keys before production deployment.
3. Review authentication mode and credential delivery behavior.
4. Apply required persistence migrations.
5. Verify login, refresh, logout, authorization, and Resource API integration.

### Common Public API Changes

The following table focuses on commonly accessed public APIs and configuration properties. Internal implementation types and advanced extension-point changes are covered in the detailed migration sections.

| Before (v0.1.x) | After (v0.2.0) |
|---|---|
| `UAuthClientProfile` | `UAuthApplicationProfile` |
| `AutoDetectClientProfile` | `AutoDetectApplicationProfile` |
| `ClientProfileModes` | `ApplicationProfileModes` |
| `IClientProfileDetector` | `IApplicationProfileDetector` |
| `IFlowClient.LoginAsync(...)` returning `Task` | `IFlowClient.LoginAsync(...)` returning `Task<UAuthResult>` |
| `TokenResponseMode` | `GrantDeliveryMode` |
| `AuthResponse.SessionIdDelivery` | `GrantDelivery.Session` |
| `AuthResponse.AccessTokenDelivery` | `GrantDelivery.AccessToken` |
| `AuthResponse.RefreshTokenDelivery` | `GrantDelivery.RefreshToken` |
| `AuthResponse.Login` | `Redirect.Login` |
| `AuthResponse.Logout` | `Redirect.Logout` |
| `ResourceApi.UAuthHubBaseUrl` | `ResourceApi.Hub.BaseUrl` |
| `ResourceApi.AllowedClientOrigins` | `ResourceApi.Cors.AllowedOrigins` |
| `ResourceApi.CorsPolicyName` | `ResourceApi.Cors.PolicyName` |

### Common Behavioral Changes

The following changes may affect existing applications even when no compilation errors occur.

| Area | Previous Behavior | v0.2.0 Behavior |
|---|---|---|
| Login submission | Navigation-based | Automatic navigation or fetch selection |
| Hybrid access token | Opaque | JWT |
| API authentication mode | PureJwt under the previous v0.2.0 resolver | Hybrid |
| Resource API authentication | Remote session validation | Hybrid remote session validation by default |
| Access-token handling | Application-managed when required | Built-in in-memory token store |
| Logout completion | Navigation-oriented submission | Response-aware completion and local credential cleanup |

Applications using the standard UltimateAuth integrations generally do not need to rewrite their login or logout implementations.

However, applications relying on specific navigation behavior, custom credential handling, or explicit authentication mode assumptions should review the corresponding migration sections.

These are API and configuration-path replacements, not guarantees of identical behavior.

**Important:** `AuthResponse` is obsolete and no longer functional. Accessing it throws `NotSupportedException`. Applications must migrate to `GrantDelivery` and `Redirect`.

Authentication modes and credential delivery now have separate responsibilities. The effective authentication mode determines which grants exist; delivery settings determine how those grants are transported.

The public `IUAuthClient` entry point and standard UltimateAuth registration methods remain available. Applications relying on built-in defaults generally do not need to replace their authentication integration.

The following sections explain the behavioral changes, security implications, and additional migration requirements in detail.

## 1. Asynchronous Authorization Policies

**Available since preview.1**

Custom implementations of `IAccessPolicy`, `IAccessInvariant`, and `IAccessAuthority` should migrate to `DecideAsync`.

**Before:**

```csharp
public AccessDecision Decide(AccessContext context)
{
    return AccessDecision.Allow();
}
```

**After:**

```csharp
public ValueTask<AccessDecision> DecideAsync(AccessContext context, CancellationToken ct = default)
{
    return ValueTask.FromResult(AccessDecision.Allow());
}
```

For `IAccessAuthority`, preserve the existing `runtimePolicies` parameter and add the cancellation token.

Synchronous `Decide` methods are obsolete. Existing synchronous implementations retain compatibility through the interface defaults, but new implementations should use `DecideAsync`.

If your application invokes an authority directly, switch to `DecideAsync` and await the result.

## 2. Authorization Check Results

**Available since preview.1**

`CheckAsync` now returns an explicit authorization decision in the response body.

If your application previously interpreted HTTP `403` as the result of a successful authorization evaluation that denied access, update that handling.

```csharp
var result = await UAuthClient.Authorization.CheckAsync(request);

if (result.IsSuccess && result.Value is { IsAllowed: true })
{
    // Authorized
}
```

An HTTP-successful authorization check does not necessarily mean that access was granted.

Inspect the returned authorization decision rather than relying solely on the HTTP status.

## 3. Custom User Lifecycle Integrations

**Available since preview.2**

The `IUserLifecycleIntegration.OnUserCreatedAsync` signature now includes `UAuthApplicationProfile`.

**Before:**

```csharp
Task OnUserCreatedAsync(
    TenantKey tenant,
    UserKey userKey,
    object request,
    CancellationToken ct = default);
```

**After:**

```csharp
Task OnUserCreatedAsync(
    TenantKey tenant,
    UserKey userKey,
    object request,
    UAuthApplicationProfile applicationProfile,
    CancellationToken ct = default);
```

Update custom implementations to accept the additional client profile parameter.

Applications using built-in lifecycle integrations do not need to make this change.

## 4. Identifier and Profile Limits

**Available since preview.2**

The reference Users domain now enforces additional identifier and profile safety limits.

The default maximum is 10 active identifiers per user. Applications requiring a different capacity should configure `Identifiers.Behavior.MaxIdentifiersPerUser`.

Existing profile creation and update operations must also respect the new field-length and metadata limits.

If you use EF Core persistence:

1. Review existing profile data for values exceeding the new limits.
2. Add or apply the appropriate EF Core database migration for your application's DbContext.
3. Verify that applications handling profile validation errors use the returned error codes.

See [Profile Validation & Limits](/docs/plugin-domains/profile-validation-limits) for the supported limits.

## 5. Password Policies and History

**Available since preview.2**

The reference password credential implementation now applies configurable password policies, with Standard as the default level.

Review custom registration, password-change, and password-reset flows to ensure that they handle server-side password validation errors.

Applications using persistent password-history storage must apply the required database migration before enabling password history.

Password history is disabled by default (`RememberLast = 0`).

See [Password Policy & History](/docs/security/password-policy) for configuration and persistence requirements.

## 6. Rate Limiting

**Available since preview.2**

Built-in endpoint rate limiting is enabled by default when using:

```csharp
app.UseUltimateAuthWithAspNetCore();
```

If your application already registers its own rate limiting middleware, avoid installing a duplicate limiter.

To retain application-owned rate limiting:

```csharp
app.UseUltimateAuthWithAspNetCore(useRateLimiting: false);
```

Then configure your existing `UseRateLimiter()` middleware in the appropriate pipeline position.

Applications using `UseUltimateAuth()` without the integrated ASP.NET Core helper do not enable UltimateAuth rate limiting by default.

Review custom HTTP clients and authentication flows for HTTP `429 Too Many Requests` handling.

See [Rate Limiting](/docs/security/rate-limiting) for middleware integration and defaults.


## 7. Native Login Form and Credential Submission

**Available since preview.3**

`UAuthLoginForm` no longer accepts `Identifier` and `Secret` component parameters.

Credentials are now read directly from native browser form inputs. This reduces unnecessary exposure of passwords through Blazor component state and Blazor Server's interactive communication.

Applications using the removed component parameters must update their login forms.

**Before:**

```razor
<UAuthLoginForm Identifier="@identifier" Secret="@password" />
```

**After — built-in form:**

```razor
<UAuthLoginForm />
```

When no child content is provided, UltimateAuth renders the identifier field, password field, and submit button automatically.

For custom layouts, provide native-compatible credential inputs:

```razor
<UAuthLoginForm>
    <input name="Identifier" autocomplete="username" required />
    <input name="Secret" type="password"
           autocomplete="current-password" required />
    <button type="submit">Sign in</button>
</UAuthLoginForm>
```

Custom inputs must use the exact HTML `name` - `Identifier` and `Secret`.

Keep credential inputs enabled during submission. Disabled inputs are excluded from native form submissions; disable the submit button instead.

The existing `TryOnly`, `TryAndCommit`, and `DirectCommit` submission modes remain available.

See [Authentication Client SDK](/docs/client-sdk/authentication) for current login integration guidance.

## 8. Authentication Failure Details

**Default changed in preview.3**

`UAuthLoginOptions.IncludeFailureDetails` now defaults to `false`.

Previously, failed authentication responses could expose lockout reasons, remaining attempts, or lockout expiration details by default.

With the new default, public authentication failures return generic `InvalidCredentials` information without exposing account-specific lockout state.

This applies to ordinary login, login previews, PKCE previews, and login failure redirects.

Applications relying on detailed failure feedback should update their user interfaces to handle generic authentication failures.

Detailed feedback remains available through explicit configuration:

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.Login.IncludeFailureDetails = true;
});
```

**Security consideration:** Enabling this option may reveal account existence or lockout state to unauthenticated clients. Keep it disabled unless detailed disclosure is an intentional application requirement.

For authorized administrative inspection, use the authentication lockout management APIs instead.

## 9. ASP.NET Core Authorization and User Status

**Behavior changed in preview.3**

UltimateAuth now checks account status when authorizing protected ASP.NET Core HTTP endpoints.

A valid session or matching role no longer automatically grants access when the associated user is inactive.

| User status | Ordinary protected HTTP endpoint |
|---|---|
| `Active` | Allowed when other requirements pass |
| `Suspended` | Denied |
| `SelfSuspended` | Denied |
| `Disabled` | Denied |
| Missing or invalid status | Denied |

Existing applications that intentionally allow suspended users to access selected protected HTTP endpoints should use:

```csharp
[Authorize]
[UAuthAllowInactive]
```

This exception preserves the endpoint's existing authentication and authorization requirements. It does not grant access to disabled or otherwise ineligible accounts.

For independently hosted Resource APIs, the validated Hub response must contain a valid `snapshot.identity.userStatus`.

Older custom Hub validation responses that omit this information are no longer sufficient for successful protected HTTP authorization.

**Authorization policy precedence:** Explicitly registered ASP.NET Core named policies are now resolved before UltimateAuth action-policy fallback. Review applications that use the same policy name in both systems.

These changes apply to ASP.NET Core HTTP authorization middleware. They do not automatically replace authorization checks in Blazor component rendering, direct service calls, or direct `IAuthorizationService.AuthorizeAsync` usage.

## 10. Password Verification and Concurrency Limiting

**Available since preview.3**

UltimateAuth introduces dummy password verification to reduce observable timing differences between authentication paths.

Password verification now also uses built-in concurrency limiting to protect CPU and memory resources.

Concurrency limiting is **enabled by default**.

The default configuration uses three coordinated policies:

| Policy | Purpose |
|---|---|
| `PasswordHashing` | Shared global hashing capacity |
| `Login` | Real and dummy login verification |
| `CredentialManagement` | Password creation, changes, resets, and history checks |

Default capacity is derived from `Math.Max(2, Environment.ProcessorCount)`. Initial queue capacity is five times the permit limit, and the queue timeout is three seconds.

When capacity is exhausted, the server may return HTTP `429 Too Many Requests` with the error code `password_verification_busy`.

Applications should treat this as a temporary server-capacity condition, not invalid credentials or an expired session.

Configure capacity based on deployment resources:

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.ConcurrencyLimiting.PasswordHashing.PermitLimit = 8;
    options.ConcurrencyLimiting.PasswordHashing.QueueLimit = 40;
    options.ConcurrencyLimiting.PasswordHashing.QueueTimeout = TimeSpan.FromSeconds(3);
});
```

The default Argon2 parallelism for newly generated hashes is now `1`.

Existing hashes remain verifiable using their stored parameters. Password resets or hash migrations are not required solely because of this default change.

Concurrency limiting is independent of HTTP endpoint rate limiting and operates per application process.

See [Concurrency Limiting](/docs/security/concurrency-limiting) for configuration and deployment considerations.

## 11. Authentication Artifact Store Capacity

**Available since preview.3**

The built-in in-memory authentication artifact store now performs periodic expiration cleanup and enforces a configurable capacity limit.

This affects temporary authentication artifacts such as PKCE authorization codes and login preview receipts.

New defaults:

| Setting | Default |
|---|---|
| `AuthArtifacts.MaxEntries` | `50,000` |
| `AuthArtifacts.CleanupInterval` | `1 minute` |

The configured capacity is per application process.

When all available entries are occupied by valid artifacts, new artifact creation can fail with HTTP `503 Service Unavailable`.

Applications with high authentication traffic should monitor artifact capacity and adjust the limits as necessary.

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.AuthArtifacts.MaxEntries = 100_000;
    options.AuthArtifacts.CleanupInterval = TimeSpan.FromMinutes(1);
});
```

The `IAuthStore` interface remains unchanged.

Custom artifact-store implementations retain responsibility for their own expiration cleanup and capacity management.

## 12. Authentication Security State Persistence

**Persistence change in preview.3**

The EF Core authentication security state implementation introduces stronger uniqueness and concurrency enforcement.

For PostgreSQL, account-level authentication security state records now use uniqueness semantics that treat null credential-type values as non-distinct.

Applications using PostgreSQL persistence must review their authentication security state data and apply the appropriate EF Core migration.

Before migration:

1. Back up the database.
2. Check for duplicate authentication security state records, particularly account-level records with a null credential type.
3. Resolve duplicates before introducing the new unique constraint.
4. Apply the migration through the application's normal EF Core deployment process.
5. Verify authentication, lockout, and password recovery operations.

The reference samples and Identity Lab include corresponding migration changes.

Applications managing their own `DbContext` must ensure that the updated model and database schema are synchronized.

Existing login and session DTO contracts remain unchanged.

## 13. Authentication Lockout and Recovery

**Available since preview.3**

UltimateAuth introduces administrative APIs for inspecting and clearing account-level and factor-level authentication lockouts.

Through `IUAuthClient.Users`, applications can now use:

```csharp
var state = await UAuthClient.Users.GetAuthenticationLockoutAsync(userKey,
    new LockoutQueryRequest(AuthenticationSecurityScope.Factor, CredentialType.Password));
```

And:

```csharp
var result = await UAuthClient.Users.UnlockAuthenticationAsync(userKey,
    new UnlockAuthenticationRequest(AuthenticationSecurityScope.Factor, CredentialType.Password));
```

These operations are authorization-protected and do not require existing applications to change their login integrations.

A successful verified password reset now clears the related password-factor lockout as part of credential recovery.

Account-level lockouts, unrelated security states, user lifecycle status, and existing session policies remain separate.

This is an additional recovery capability rather than a breaking API change.

See [Authentication Lockout & Recovery](/docs/security/authentication-lockout).

## 14. Additional Authentication Security Hardening

**Available since preview.3**

Several authentication checks have been strengthened:

- Relative return URLs remain supported, while absolute return URLs require an explicitly allowed origin.
- Ambiguous or unsafe return URL paths are rejected.
- Login preview receipts are bound to the original authentication context.
- Preview receipts must be consumed successfully and atomically before they can suppress duplicate failed-attempt accounting.
- Previously consumed, mismatched, or stale preview receipts cannot bypass failure accounting.

Applications using standard UltimateAuth login components should not need additional code changes.

Custom login clients should avoid reusing preview receipts or modifying the authentication context between preview and commit.

Applications relying on arbitrary external redirect targets must explicitly configure the corresponding allowed origins.

These changes intentionally strengthen validation and may reject requests that were previously accepted.

## 15. Device Limits and Browser Device Type Classification

**Available since rc.1**

UltimateAuth introduces configurable active-device limits through `UAuthServerOptions.DeviceLimits`.

Applications can restrict the number of distinct active devices per user and tenant, either globally or by device type.

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.DeviceLimits.MaxDevices = 3;
    options.DeviceLimits.TypeLimits["web"] = 2;
    options.DeviceLimits.Behavior = DeviceLimitBehavior.RejectNewLogin;
});
```

Device limits are **disabled by default**:

- `MaxDevices = null`
- `TypeLimits` is empty.
- `Behavior = RejectNewLogin`

Existing applications do not acquire device quotas merely by upgrading.

When enabled, `RejectNewLogin` refuses additional device admission without revoking existing devices.

`RevokeOldest` instead revokes eligible older active device chains when capacity must be freed.

### Breaking Change: Browser Device Type Is Now `web`

**Browser-based clients previously could be classified as `desktop`. The built-in Blazor web device provider now reports `DeviceType = "web"`.**

Server device-type resolution also defaults to `web` when no explicit type is supplied.

This applies to both desktop and mobile browsers.

| Client Environment | DeviceType |
|---|---|
| Desktop browser | `web` |
| Mobile browser | `web` |
| Native desktop application | `desktop` when explicitly provided |
| Native mobile application | `mobile` when explicitly provided |

The change distinguishes browser-based client environments from native application platforms.

It does not remove the `desktop` or `mobile` classifications.

Applications can continue using these values for appropriate native clients.

### Migration Impact

This is a **behavioral breaking change** for applications that rely on device-type classification.

Review implementations that:

- Filter sessions by `DeviceType`.
- Display device types in user interfaces.
- Apply custom device-type policies.
- Use device classifications in analytics or diagnostics.
- Assume that `desktop` represents all desktop-browser sessions.

For example:

**Before:**

```csharp
var browserType = "desktop";
```

**After:**

```csharp
var browserType = "web";
```

Do not infer the operating system from `DeviceType`.

Use the separate `Platform`, `OperatingSystem`, and `Browser` metadata where appropriate.

**Note:** Device Limits is a new feature introduced in v0.2.0. The example above illustrates migration of existing device-type assumptions, not an earlier `DeviceLimits.TypeLimits` API.

### Existing Persisted Device Records

Updating UltimateAuth does not automatically rewrite device-type values in persisted session chains.

An existing browser device may still be recorded as:

```text
DeviceType: desktop
```

When an incoming `DeviceId` matches an already active device chain, UltimateAuth preserves that device's existing type classification.

Therefore, a previously admitted browser device classified as `desktop` can retain that classification during subsequent authentication.

New browser device IDs are classified as `web`.

During the transition, both classifications may coexist:

```text
Existing active browser:
    DeviceType = desktop

New browser:
    DeviceType = web
```

This distinction matters when per-type limits are enabled.

Legacy `desktop` records and new `web` records may be counted in different type categories until the existing active device state ends.

Applications should review existing session data and plan an appropriate transition.

If immediate classification consistency is required, consider controlled reauthentication or device-session revocation.

Do not assume that a database schema migration automatically changes stored device classifications.

### Breaking Change: Custom Session Stores

The `ISessionStore` interface introduces a new operation:

```csharp
Task<TResult> ExecuteAdmissionAsync<TResult>(
    Func<CancellationToken, Task<TResult>> action,
    CancellationToken ct = default);
```

This is an **interface-level breaking change** for custom session-store implementations.

Implementations must add support for the new method even when device limits are disabled.

When limits are enabled, device admission must be atomic and concurrency-safe.

Custom stores must ensure:

- Admission changes are committed atomically.
- Failed admissions are rolled back.
- Simultaneous login requests cannot exceed configured limits.
- Concurrency protection applies across application instances sharing the same persistence infrastructure.

The built-in in-memory and EF Core stores implement the new contract.

The EF Core implementation uses a serializable transaction for device admission.

### Database Migration Requirements

Device Limits does not introduce a new database table or require a schema migration by itself.

The feature uses existing session root, chain, and session persistence.

However, other v0.2.0 persistence changes may still require application database migrations.

Custom `DbContext` implementations should continue following the database migration requirements documented in the preceding sections.

### Upgrade Checklist

1. Review custom device-type consumers and replace browser-specific `desktop` assumptions with `web`.
2. Review active persisted device chains for legacy `desktop` classifications.
3. Plan session turnover or controlled revocation if immediate classification consistency is required.
4. Update custom `ISessionStore` implementations to support `ExecuteAdmissionAsync`.
5. Verify atomic admission and concurrent login handling before enabling device quotas.
6. Configure `DeviceLimits` explicitly only when the application requires device restrictions.
7. Test login failure handling and device management behavior with the selected `RejectNewLogin` or `RevokeOldest` policy.

See [Device Limits](/docs/sessions-devices/device-limits) for the complete configuration and enforcement reference.

## 16. Application Profile API Redesign

**Introduced in the PureJwt implementation for v0.2.0**

`UAuthClientProfile` has been replaced by `UAuthApplicationProfile`.

The new name distinguishes the application environment from the authentication mode selected by the server.

**Before:**

```csharp
options.ClientProfile = UAuthClientProfile.BlazorServer;
```

**After:**

```csharp
options.ApplicationProfile = UAuthApplicationProfile.BlazorServer;
```

Applications using automatic profile detection normally do not need to configure this property.

Custom implementations of `IClientProfileDetector` must migrate to `IApplicationProfileDetector`. Methods and contracts that previously accepted `UAuthClientProfile` now use the replacement enum.

The new enum also distinguishes a Resource API from an ordinary API consumer through `UAuthApplicationProfile.ResourceApi`.

### Authentication mode selection

The server now supports explicit mode selection:

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.AuthMode = UAuthMode.PureOpaque;
});
```

For profile-specific customization:

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.ApplicationProfileModes[UAuthApplicationProfile.BlazorServer] = UAuthMode.PureOpaque;

    options.ApplicationProfileModes[UAuthApplicationProfile.BlazorWasm] = UAuthMode.PureJwt;
});
```

`AuthMode` and `ApplicationProfileModes` cannot be configured together.

`AllowedModes` remains an allowlist, **not** an authentication mode selector.

Applications relying on automatic resolution can keep their existing approach, but should verify the effective mode for each supported application profile.

Client-supplied profile information must not be treated as proof of application identity or trust.

## 17. Authentication Response and Grant Delivery Redesign

**Breaking configuration change in the PureJwt implementation**

The former `AuthResponse` configuration has been replaced by two independent groups:

- `GrantDelivery` configures how authentication credentials are returned.
- `Redirect` configures navigation after login and logout.

The legacy `UAuthServerOptions.AuthResponse` property is obsolete and throws `NotSupportedException` when accessed.

Applications that explicitly configured authentication responses must update those settings.

### Credential delivery

**Before:**

```csharp
options.AuthResponse.AccessTokenDelivery.Mode = TokenResponseMode.Header;
```

**After:**

```csharp
options.GrantDelivery.AccessToken.Mode = GrantDeliveryMode.Header;
```

A global preference is also available:

```csharp
options.GrantDelivery.Default = GrantDeliveryMode.Cookie;
```

Individual grant settings take precedence over the global preference.

When no explicit delivery preference is configured, UltimateAuth uses the effective authentication mode and application profile to select its defaults.

`GrantDeliveryMode` replaces `TokenResponseMode`.

The configuration is intentionally more restrictive:

- Delivery settings do not create credentials that are unavailable in the selected authentication mode.
- A required grant cannot be disabled using `GrantDeliveryMode.None`.
- `GrantDeliveryMode.Body` is not supported by the current grant delivery resolver.
- Header names and formats can be customized through the corresponding grant options.
- Cookie attributes remain configurable through `options.Cookie`.

Applications using built-in response defaults generally do not need to configure grant delivery explicitly.

Applications using custom cookie or header handling should verify that their request-side credential resolution matches the configured response delivery.

### Login and logout redirects

**Before:**

```csharp
options.AuthResponse.Login.SuccessRedirect = "/dashboard";
options.AuthResponse.Logout.SuccessRedirect = "/";
```

**After:**

```csharp
options.Redirect.Login.SuccessRedirect = "/dashboard";
options.Redirect.Logout.SuccessRedirect = "/";
```

Redirect configuration no longer controls credential delivery.

The legacy `LoginRedirectOptions` properties `FailureQueryKey`, `CodeQueryKey`, `FailureCodes`, `IncludeLockoutTiming`, and `IncludeRemainingAttempts` have been removed.

Applications that used these options must remove the corresponding configuration and adapt to the supported redirect behavior.

For authentication failure disclosure, review the `Login.IncludeFailureDetails` setting and the security considerations described in Section 8.

### Automatic mode resolution

The selected authentication mode now determines which grants are available before delivery configuration is applied.

Do not assume that selecting cookie or header delivery changes the authentication mode or the issued token format.

Review applications that previously depended on response configuration to override mode-specific credential behavior.

## 18. Production Cryptographic Key Configuration

**Security-sensitive deployment change in the PureJwt implementation**

UltimateAuth now separates JWT signing from server-managed token hashing.

The built-in cryptography configuration provides two independent keys:

| Option | Purpose |
|---|---|
| `Cryptography.TokenHashingKey` | HMAC-SHA256 hashing of server-managed token material |
| `Cryptography.JwtSigningKey` | HS256 JWT access-token signing |

The built-in implementations require valid Base64-encoded key material containing at least 32 bytes per key.

The keys must be different.

### Production startup validation

UltimateAuth includes deterministic cryptographic defaults for local development.

These defaults are accepted in the `Development` environment but are rejected outside Development when the corresponding built-in provider is used.

**Applications that previously started without explicit production cryptographic configuration must now provide securely generated keys.**

For example:

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.Cryptography.TokenHashingKey = builder.Configuration["UltimateAuth:Cryptography:TokenHashingKey"]
        ?? throw new InvalidOperationException("Token hashing key is missing.");

    options.Cryptography.JwtSigningKey = builder.Configuration["UltimateAuth:Cryptography:JwtSigningKey"]
        ?? throw new InvalidOperationException("JWT signing key is missing.");
});
```

Supply the values through a secret manager or environment variables:

```text
UltimateAuth__Cryptography__TokenHashingKey
UltimateAuth__Cryptography__JwtSigningKey
```

Generate independent random values using a cryptographically secure random-number generator.

Do not commit production keys to source control or generate new keys on every application startup.

Applications using custom registered signing or hashing providers should review the corresponding provider registrations and validation requirements.

### Existing token compatibility

Earlier built-in token hashing depended on the JWT signing key provider.

The new implementation uses a separate `TokenHashingKey`.

**Changing the effective token-hashing key can invalidate existing server-managed token credentials whose stored hashes were produced using the previous key.**

This can affect existing sessions or refresh credentials, depending on the application's active authentication mode and persistence configuration.

Plan an appropriate reauthentication strategy before deploying the new key configuration.

Keep key material consistent across application instances that share authentication state.

JWT signing-key changes can also invalidate previously issued JWTs unless the corresponding verification keys remain available through an explicitly configured validation strategy.

See [Token Security](/docs/security/token-security) and [Real-World Setup](/docs/getting-started/real-world-setup) for current cryptographic configuration guidance.

## 19. PureJwt Authentication and Resource API Migration

**New authentication mode implementation in v0.2.0**

`PureJwt` now supports authentication without creating server-side sessions.

It issues JWT access tokens and uses persisted, device-associated refresh-token chains for renewal.

`PureOpaque` and the existing session-backed authentication paths remain available.

`SemiHybrid` is not yet supported by the current implementation.

### PureJwt authentication behavior

Unlike session-backed modes, PureJwt does not require a `SessionId` or `SessionChainId` to issue or refresh credentials.

The JWT access token represents the authenticated identity and can be validated using trusted verification keys.

The refresh credential remains stateful.

PureJwt refresh:

1. Validates the refresh token, tenant, and device association.
2. Confirms that the refresh credential is not session-bound.
3. Rotates the refresh token and persists its replacement.
4. Issues a new JWT access token.

An invalid, expired, revoked, or incorrectly bound refresh credential cannot continue the authentication flow.

Refresh-token replay detection can revoke the associated refresh chain.

### PureJwt logout

PureJwt logout differs from session-based logout.

When the authenticated request supplies a refresh token, UltimateAuth validates its ownership and revokes the associated refresh chain.

Clients must ensure that the applicable refresh credential is supplied when they expect logout to terminate server-managed refresh capability.

Clearing a cookie or deleting a locally stored token is not equivalent to revoking refresh-token state.

**Previously issued JWT access tokens remain independently valid until expiration**, unless an additional validation or revocation mechanism prevents their acceptance.

Consequently, PureJwt logout must not be treated as immediate revocation of every already-issued access token.

### Resource API configuration

`UAuthResourceApiOptions` has been reorganized.

**Before:**

```csharp
options.UAuthHubBaseUrl = "https://auth.example.com";
options.AllowedClientOrigins.Add("https://app.example.com");
options.CorsPolicyName = "UAuthResource";
```

**After:**

```csharp
options.Hub.BaseUrl = "https://auth.example.com";
options.Cors.AllowedOrigins.Add("https://app.example.com");
options.Cors.PolicyName = "UAuthResource";
```

Resource API authentication settings are now grouped under `options.Auth`.

For a PureJwt Resource API, configure the JWT validation parameters and trusted verification keys:

```csharp
builder.Services.AddUltimateAuthResourceApi(options =>
{
    options.Auth.Mode = UAuthMode.PureJwt;

    options.Auth.Jwt = new UAuthJwtValidationOptions
    {
        Issuer = "UAuth",
        Audience = "UAuthClient",
        ValidAlgorithms = [SecurityAlgorithms.HmacSha256]
    };

    options.Cryptography.JwtVerificationKeys.Add(
        new UAuthJwtVerificationKeyOptions
        {
            KeyId = "uauth-hs256-v1",
            Key = builder.Configuration["UltimateAuth:JwtVerificationKey"]
                ?? throw new InvalidOperationException("JWT verification key is missing.")
        });
});
```

The issuer, audience, algorithm, key ID, and key material must match the issuing authority's configuration.

When using the built-in symmetric signing implementation, the trusted Resource API verification key contains the same cryptographic key material as the authority's JWT signing key.

Do not configure the server's token-hashing key as a Resource API verification key.

### Remote versus local authentication

The built-in authentication mode resolver now selects PureOpaque for BlazorServer and Hybrid for all other application profiles.

Resource APIs default to Hybrid.

Existing applications using remote session validation can continue using session-backed authentication by configuring the Hub address.

```csharp
builder.Services.AddUltimateAuthResourceApi(options =>
{
    options.Hub.BaseUrl = "https://auth.example.com";
});
```

The default incoming session credential transport is cookie-based.

PureJwt must be explicitly selected when independent JWT validation is required:

```csharp
options.Auth.Mode = UAuthMode.PureJwt;
```

The issuing authentication server must also be configured to issue compatible PureJwt credentials.

Although Hybrid now issues JWT access tokens, the current Hybrid Resource API implementation continues to use remote session validation.

Hybrid-aware JWT validation in separate Resource APIs is not yet supported.

UAuthHub and Resource APIs resolve their authentication modes independently. Automatic authentication configuration discovery and mode negotiation are not currently supported.

Applications should verify authentication mode compatibility, cookie scope, credential transport, and CORS configuration before deployment.

## 20. Refresh Token Persistence and Database Migration

**Persistence and custom-store breaking change in the PureJwt implementation**

Refresh-token persistence now supports both session-backed credentials and session-independent PureJwt refresh chains.

The refresh-token model introduces `RefreshChainId` and additional device and authentication metadata.

`SessionId` is now nullable, and the previous `ChainId` association is explicitly named `SessionChainId`.

### EF Core schema changes

Applications using UltimateAuth's EF Core token persistence must update their database schema before deploying the new runtime.

The reference migrations introduce:

| Change | Description |
|---|---|
| `ChainId` → `SessionChainId` | Renamed session-chain association |
| `SessionId` | Nullable to support PureJwt |
| `RefreshChainId` | New required refresh-chain identifier |
| `DeviceId` | New nullable device association |
| `AuthenticatedAt` | New nullable authentication timestamp |
| Indexes | Additional refresh-chain and device lookup indexes |

The reference migrations are provided for the sample applications and Identity Lab.

Applications using their own `DbContext` must generate and review the corresponding EF Core migration.

### Existing refresh-token records

**Important:** The generated reference migrations introduce `RefreshChainId` as a required column with `Guid.Empty` as the default for pre-existing rows.

This default supports schema migration but does not establish valid, distinct refresh-chain identities for existing tokens.

Do not assume previously persisted refresh credentials remain compatible with the new token model.

Before production migration:

1. Back up the authentication database.
2. Review existing refresh-token rows and their session or chain associations.
3. Decide whether existing refresh credentials should be invalidated or migrated using a reviewed, data-preserving procedure.
4. Avoid treating `Guid.Empty` as a valid refresh-chain identifier.
5. Apply the schema migration before deploying the runtime that expects the new model.
6. Verify login, refresh, logout, and replay handling after deployment.

If existing refresh credentials are intentionally invalidated, applications must allow affected users to authenticate again.

Do not use the example migrations as proof that all existing refresh-token records have been semantically migrated.

### Custom refresh-token stores

The `IRefreshTokenStore` contract now distinguishes session-chain and refresh-chain revocation.

**Before:**

```csharp
RevokeByChainAsync(...)
```

**After:**

```csharp
RevokeBySessionChainAsync(...)
RevokeByRefreshChainAsync(...)
```

Custom implementations must support the revised contract.

The refresh-chain operation must revoke only the intended refresh-token lineage within the applicable tenant.

Applications with custom token projections, mappers, validators, or issuance services must also account for the new nullable session association and refresh-chain identity.

The built-in EF Core and in-memory token stores implement the updated contracts.

## 21. Custom Integrations and Compatibility Review

**Additional API and contract changes in the PureJwt implementation**

The changes in this section primarily affect applications replacing or extending UltimateAuth's built-in implementations.

Applications using the standard client and server registration methods generally do not need to implement these interfaces.

### Token context and refresh results

Several public token-related contracts now distinguish session chains from refresh chains.

For custom integrations, review:

- `TokenIssuanceContext.ChainId` → `TokenIssuanceContext.SessionChainId`
- `RefreshTokenRotationExecution.ChainId` → `RefreshTokenRotationExecution.SessionChainId`
- `RefreshTokenValidationResult.ChainId` → `RefreshTokenValidationResult.SessionChainId`
- `RefreshToken.ChainId` → `RefreshToken.SessionChainId`

The new `RefreshChainId` is a separate identity. It must not be treated as an interchangeable replacement for `SessionChainId`.

PureJwt token issuance and validation can operate without a server-side session, whereas session-backed modes preserve their session associations.

### Custom authentication and response components

Custom implementations using the previous application profile, authentication mode resolver, credential resolver, or response-delivery contracts must be reviewed for signature and behavior changes.

In particular:

- Authentication mode resolution now uses an explicit `AuthModeResolutionContext`.
- Effective grant delivery uses `EffectiveGrantDelivery` rather than the legacy credential-response options.
- JWT-based authentication requires verification of trusted claims and device binding.
- PureJwt authorization must not assume that a session ID exists.

Applications with direct dependencies on these extension points should compile and run their integration tests against v0.2.0 before deployment.

### Compatibility testing

For customized deployments, verify the following scenarios against the selected authentication mode:

1. Initial login and credential issuance.
2. Authenticated request validation.
3. Refresh and token rotation.
4. Logout and refresh-chain termination.
5. Authorization for protected HTTP endpoints.
6. Device mismatch handling.
7. Restart and multi-instance persistence behavior.
8. Resource API authentication and CORS configuration.

These checks are especially important when upgrading implementations that previously assumed all authentication contexts were backed by server-side sessions.

## 22. Login Transport and Client API Changes

**Authentication client changes in v0.2.0**

UltimateAuth now supports both navigation-based and fetch-based login submission.

The client discovers the effective server capabilities and selects a compatible login transport automatically.

### LoginAsync return type

The return type of `IFlowClient.LoginAsync` has changed.

**Before:**

```csharp
Task LoginAsync(LoginRequest request, string? returnUrl = null);
```

**After:**

```csharp
Task<UAuthResult> LoginAsync(
    LoginRequest request,
    string? returnUrl = null,
    UAuthLoginTransport transport = UAuthLoginTransport.Auto);
```

Existing awaited calls remain source-compatible:

```csharp
await UAuthClient.Flows.LoginAsync(request);
```

Applications can now inspect the returned result:

```csharp
var result = await UAuthClient.Flows.LoginAsync(request);
```

For navigation-based submissions, successful submission does not itself confirm that the server has accepted the authentication credentials.

Fetch-based submissions allow the client to observe the authentication response and process the delivered credentials.

Custom `IFlowClient` implementations, test doubles, and mocks must be updated to match the new method signature.

### TryLoginAsync signature

`TryLoginAsync` now accepts an optional login transport parameter:

```csharp
Task<TryLoginResult> TryLoginAsync(
    LoginRequest request,
    UAuthSubmitMode mode,
    string? returnUrl = null,
    UAuthLoginTransport transport = UAuthLoginTransport.Auto);
```

The existing `TryOnly`, `TryAndCommit`, and `DirectCommit` submission modes remain available.

Existing application calls do not need to specify the new parameter.

### Explicit login transport

Applications can explicitly select a transport when necessary:

```csharp
await UAuthClient.Flows.LoginAsync(
    request,
    transport: UAuthLoginTransport.Fetch);
```

The available transport strategies are:

- `Auto`
- `Fetch`
- `Navigation`

`Auto` is the default and recommended strategy.

Applications must not assume that every login operation performs a full browser navigation.

### Login transport discovery endpoint

A new endpoint exposes the effective login transport capabilities:

```text
/auth/login/transport
```

Applications using custom endpoint paths can configure:

```csharp
options.Endpoints.LoginTransport = "/login/transport";
```

Review reverse proxies, endpoint allowlists, and custom authentication endpoint configurations to ensure that this endpoint is accessible to the client.

### Custom client implementations

The `IFlowClient` contract also introduces:

```csharp
Task<RefreshResult> RecoverAsync();
```

This operation supports authentication recovery when a usable access token is unavailable but a compatible refresh credential remains available.

Custom client implementations must implement the updated contract.

Applications using the built-in UltimateAuth client do not need to implement recovery manually.
