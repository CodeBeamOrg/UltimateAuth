# Migrating to v0.2.0

**Migration Impact: Medium — In Progress**

**Latest published prerelease reviewed: v0.2.0-preview.2**

This guide covers migration requirements for the upcoming UltimateAuth v0.2.0 release.

The guide is provisional and will be updated as new preview and release candidate versions become available. The final migration requirements may change before the stable v0.2.0 release.

## 1. Asynchronous Authorization Policies

**Available since preview.1**

Custom implementations of `IAccessPolicy`, `IAccessInvariant`, and `IAccessAuthority` should migrate to `DecideAsync`.

**Before:**

```csharp
public AccessDecision Decide(AccessContext context)
{
    return AccessDecision.Allow();
}
```

**After:**

```csharp
public ValueTask<AccessDecision> DecideAsync(AccessContext context, CancellationToken ct = default)
{
    return ValueTask.FromResult(AccessDecision.Allow());
}
```

For `IAccessAuthority`, preserve the existing `runtimePolicies` parameter and add the cancellation token.

Synchronous `Decide` methods are obsolete. Existing synchronous implementations retain compatibility through the interface defaults, but new implementations should use `DecideAsync`.

If your application invokes an authority directly, switch to `DecideAsync` and await the result.

## 2. Authorization Check Results

**Available since preview.1**

`CheckAsync` now returns an explicit authorization decision in the response body.

If your application previously interpreted HTTP `403` as the result of a successful authorization evaluation that denied access, update that handling.

```csharp
var result = await UAuthClient.Authorization.CheckAsync(request);

if (result.IsSuccess && result.Value is { IsAllowed: true })
{
    // Authorized
}
```

An HTTP-successful authorization check does not necessarily mean that access was granted.

Inspect the returned authorization decision rather than relying solely on the HTTP status.

## 3. Custom User Lifecycle Integrations

**Available since preview.2**

The `IUserLifecycleIntegration.OnUserCreatedAsync` signature now includes `UAuthClientProfile`.

**Before:**

```csharp
Task OnUserCreatedAsync(
    TenantKey tenant,
    UserKey userKey,
    object request,
    CancellationToken ct = default);
```

**After:**

```csharp
Task OnUserCreatedAsync(
    TenantKey tenant,
    UserKey userKey,
    object request,
    UAuthClientProfile clientProfile,
    CancellationToken ct = default);
```

Update custom implementations to accept the additional client profile parameter.

Applications using built-in lifecycle integrations do not need to make this change.

## 4. Identifier and Profile Limits

**Available since preview.2**

The reference Users domain now enforces additional identifier and profile safety limits.

The default maximum is 10 active identifiers per user. Applications requiring a different capacity should configure `Identifiers.Behavior.MaxIdentifiersPerUser`.

Existing profile creation and update operations must also respect the new field-length and metadata limits.

If you use EF Core persistence:

1. Review existing profile data for values exceeding the new limits.
2. Add or apply the appropriate EF Core database migration for your application's DbContext.
3. Verify that applications handling profile validation errors use the returned error codes.

See [Profile Validation & Limits](/docs/plugin-domains/profile-validation-limits) for the supported limits.

## 5. Password Policies and History

**Available since preview.2**

The reference password credential implementation now applies configurable password policies, with Standard as the default level.

Review custom registration, password-change, and password-reset flows to ensure that they handle server-side password validation errors.

Applications using persistent password-history storage must apply the required database migration before enabling password history.

Password history is disabled by default (`RememberLast = 0`).

See [Password Policy & History](/docs/security/password-policy) for configuration and persistence requirements.

## 6. Rate Limiting

**Available since preview.2**

Built-in endpoint rate limiting is enabled by default when using:

```csharp
app.UseUltimateAuthWithAspNetCore();
```

If your application already registers its own rate limiting middleware, avoid installing a duplicate limiter.

To retain application-owned rate limiting:

```csharp
app.UseUltimateAuthWithAspNetCore(useRateLimiting: false);
```

Then configure your existing `UseRateLimiter()` middleware in the appropriate pipeline position.

Applications using `UseUltimateAuth()` without the integrated ASP.NET Core helper do not enable UltimateAuth rate limiting by default.

Review custom HTTP clients and authentication flows for HTTP `429 Too Many Requests` handling.

See [Rate Limiting](/docs/security/rate-limiting) for middleware integration and defaults.


## 7. Native Login Form and Credential Submission

**Available since preview.3**

`UAuthLoginForm` no longer accepts `Identifier` and `Secret` component parameters.

Credentials are now read directly from native browser form inputs. This reduces unnecessary exposure of passwords through Blazor component state and Blazor Server's interactive communication.

Applications using the removed component parameters must update their login forms.

**Before:**

```razor
<UAuthLoginForm Identifier="@identifier" Secret="@password" />
```

**After — built-in form:**

```razor
<UAuthLoginForm />
```

When no child content is provided, UltimateAuth renders the identifier field, password field, and submit button automatically.

For custom layouts, provide native-compatible credential inputs:

```razor
<UAuthLoginForm>
    <input name="Identifier" autocomplete="username" required />
    <input name="Secret" type="password"
           autocomplete="current-password" required />
    <button type="submit">Sign in</button>
</UAuthLoginForm>
```

Custom inputs must use the exact HTML `name` - `Identifier` and `Secret`.

Keep credential inputs enabled during submission. Disabled inputs are excluded from native form submissions; disable the submit button instead.

The existing `TryOnly`, `TryAndCommit`, and `DirectCommit` submission modes remain available.

See [Authentication Client SDK](/docs/client-sdk/authentication) for current login integration guidance.

## 8. Authentication Failure Details

**Default changed in preview.3**

`UAuthLoginOptions.IncludeFailureDetails` now defaults to `false`.

Previously, failed authentication responses could expose lockout reasons, remaining attempts, or lockout expiration details by default.

With the new default, public authentication failures return generic `InvalidCredentials` information without exposing account-specific lockout state.

This applies to ordinary login, login previews, PKCE previews, and login failure redirects.

Applications relying on detailed failure feedback should update their user interfaces to handle generic authentication failures.

Detailed feedback remains available through explicit configuration:

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.Login.IncludeFailureDetails = true;
});
```

**Security consideration:** Enabling this option may reveal account existence or lockout state to unauthenticated clients. Keep it disabled unless detailed disclosure is an intentional application requirement.

For authorized administrative inspection, use the authentication lockout management APIs instead.

## 9. ASP.NET Core Authorization and User Status

**Behavior changed in preview.3**

UltimateAuth now checks account status when authorizing protected ASP.NET Core HTTP endpoints.

A valid session or matching role no longer automatically grants access when the associated user is inactive.

| User status | Ordinary protected HTTP endpoint |
|---|---|
| `Active` | Allowed when other requirements pass |
| `Suspended` | Denied |
| `SelfSuspended` | Denied |
| `Disabled` | Denied |
| Missing or invalid status | Denied |

Existing applications that intentionally allow suspended users to access selected protected HTTP endpoints should use:

```csharp
[Authorize]
[UAuthAllowInactive]
```

This exception preserves the endpoint's existing authentication and authorization requirements. It does not grant access to disabled or otherwise ineligible accounts.

For independently hosted Resource APIs, the validated Hub response must contain a valid `snapshot.identity.userStatus`.

Older custom Hub validation responses that omit this information are no longer sufficient for successful protected HTTP authorization.

**Authorization policy precedence:** Explicitly registered ASP.NET Core named policies are now resolved before UltimateAuth action-policy fallback. Review applications that use the same policy name in both systems.

These changes apply to ASP.NET Core HTTP authorization middleware. They do not automatically replace authorization checks in Blazor component rendering, direct service calls, or direct `IAuthorizationService.AuthorizeAsync` usage.

## 10. Password Verification and Concurrency Limiting

**Available since preview.3**

UltimateAuth introduces dummy password verification to reduce observable timing differences between authentication paths.

Password verification now also uses built-in concurrency limiting to protect CPU and memory resources.

Concurrency limiting is **enabled by default**.

The default configuration uses three coordinated policies:

| Policy | Purpose |
|---|---|
| `PasswordHashing` | Shared global hashing capacity |
| `Login` | Real and dummy login verification |
| `CredentialManagement` | Password creation, changes, resets, and history checks |

Default capacity is derived from `Math.Max(2, Environment.ProcessorCount)`. Initial queue capacity is five times the permit limit, and the queue timeout is three seconds.

When capacity is exhausted, the server may return HTTP `429 Too Many Requests` with the error code `password_verification_busy`.

Applications should treat this as a temporary server-capacity condition, not invalid credentials or an expired session.

Configure capacity based on deployment resources:

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.ConcurrencyLimiting.PasswordHashing.PermitLimit = 8;
    options.ConcurrencyLimiting.PasswordHashing.QueueLimit = 40;
    options.ConcurrencyLimiting.PasswordHashing.QueueTimeout = TimeSpan.FromSeconds(3);
});
```

The default Argon2 parallelism for newly generated hashes is now `1`.

Existing hashes remain verifiable using their stored parameters. Password resets or hash migrations are not required solely because of this default change.

Concurrency limiting is independent of HTTP endpoint rate limiting and operates per application process.

See [Concurrency Limiting](/docs/security/concurrency-limiting) for configuration and deployment considerations.

## 11. Authentication Artifact Store Capacity

**Available since preview.3**

The built-in in-memory authentication artifact store now performs periodic expiration cleanup and enforces a configurable capacity limit.

This affects temporary authentication artifacts such as PKCE authorization codes and login preview receipts.

New defaults:

| Setting | Default |
|---|---|
| `AuthArtifacts.MaxEntries` | `50,000` |
| `AuthArtifacts.CleanupInterval` | `1 minute` |

The configured capacity is per application process.

When all available entries are occupied by valid artifacts, new artifact creation can fail with HTTP `503 Service Unavailable`.

Applications with high authentication traffic should monitor artifact capacity and adjust the limits as necessary.

```csharp
builder.Services.AddUltimateAuthServer(options =>
{
    options.AuthArtifacts.MaxEntries = 100_000;
    options.AuthArtifacts.CleanupInterval = TimeSpan.FromMinutes(1);
});
```

The `IAuthStore` interface remains unchanged.

Custom artifact-store implementations retain responsibility for their own expiration cleanup and capacity management.

## 12. Authentication Security State Persistence

**Persistence change in preview.3**

The EF Core authentication security state implementation introduces stronger uniqueness and concurrency enforcement.

For PostgreSQL, account-level authentication security state records now use uniqueness semantics that treat null credential-type values as non-distinct.

Applications using PostgreSQL persistence must review their authentication security state data and apply the appropriate EF Core migration.

Before migration:

1. Back up the database.
2. Check for duplicate authentication security state records, particularly account-level records with a null credential type.
3. Resolve duplicates before introducing the new unique constraint.
4. Apply the migration through the application's normal EF Core deployment process.
5. Verify authentication, lockout, and password recovery operations.

The reference samples and Identity Lab include corresponding migration changes.

Applications managing their own `DbContext` must ensure that the updated model and database schema are synchronized.

Existing login and session DTO contracts remain unchanged.

## 13. Authentication Lockout and Recovery

**Available since preview.3**

UltimateAuth introduces administrative APIs for inspecting and clearing account-level and factor-level authentication lockouts.

Through `IUAuthClient.Users`, applications can now use:

```csharp
var state = await UAuthClient.Users.GetAuthenticationLockoutAsync(userKey,
    new LockoutQueryRequest(AuthenticationSecurityScope.Factor, CredentialType.Password));
```

And:

```csharp
var result = await UAuthClient.Users.UnlockAuthenticationAsync(userKey,
    new UnlockAuthenticationRequest(AuthenticationSecurityScope.Factor, CredentialType.Password));
```

These operations are authorization-protected and do not require existing applications to change their login integrations.

A successful verified password reset now clears the related password-factor lockout as part of credential recovery.

Account-level lockouts, unrelated security states, user lifecycle status, and existing session policies remain separate.

This is an additional recovery capability rather than a breaking API change.

See [Authentication Lockout & Recovery](/docs/security/authentication-lockout).

## 14. Additional Authentication Security Hardening

**Available since preview.3**

Several authentication checks have been strengthened:

- Relative return URLs remain supported, while absolute return URLs require an explicitly allowed origin.
- Ambiguous or unsafe return URL paths are rejected.
- Login preview receipts are bound to the original authentication context.
- Preview receipts must be consumed successfully and atomically before they can suppress duplicate failed-attempt accounting.
- Previously consumed, mismatched, or stale preview receipts cannot bypass failure accounting.

Applications using standard UltimateAuth login components should not need additional code changes.

Custom login clients should avoid reusing preview receipts or modifying the authentication context between preview and commit.

Applications relying on arbitrary external redirect targets must explicitly configure the corresponding allowed origins.

These changes intentionally strengthen validation and may reject requests that were previously accepted.
