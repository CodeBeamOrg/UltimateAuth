# Migrating to v0.2.0

**Migration Impact: Medium — In Progress**

**Latest published prerelease reviewed: v0.2.0-preview.2**

This guide covers migration requirements for the upcoming UltimateAuth v0.2.0 release.

The guide is provisional and will be updated as new preview and release candidate versions become available. The final migration requirements may change before the stable v0.2.0 release.

## 1. Asynchronous Authorization Policies

**Available since preview.1**

Custom implementations of `IAccessPolicy`, `IAccessInvariant`, and `IAccessAuthority` should migrate to `DecideAsync`.

**Before:**

```csharp
public AccessDecision Decide(AccessContext context)
{
    return AccessDecision.Allow();
}
```

**After:**

```csharp
public ValueTask<AccessDecision> DecideAsync(AccessContext context, CancellationToken ct = default)
{
    return ValueTask.FromResult(AccessDecision.Allow());
}
```

For `IAccessAuthority`, preserve the existing `runtimePolicies` parameter and add the cancellation token.

Synchronous `Decide` methods are obsolete. Existing synchronous implementations retain compatibility through the interface defaults, but new implementations should use `DecideAsync`.

If your application invokes an authority directly, switch to `DecideAsync` and await the result.

## 2. Authorization Check Results

**Available since preview.1**

`CheckAsync` now returns an explicit authorization decision in the response body.

If your application previously interpreted HTTP `403` as the result of a successful authorization evaluation that denied access, update that handling.

```csharp
var result = await UAuthClient.Authorization.CheckAsync(request);

if (result.IsSuccess && result.Value is { IsAllowed: true })
{
    // Authorized
}
```

An HTTP-successful authorization check does not necessarily mean that access was granted.

Inspect the returned authorization decision rather than relying solely on the HTTP status.

## 3. Custom User Lifecycle Integrations

**Available since preview.2**

The `IUserLifecycleIntegration.OnUserCreatedAsync` signature now includes `UAuthClientProfile`.

**Before:**

```csharp
Task OnUserCreatedAsync(
    TenantKey tenant,
    UserKey userKey,
    object request,
    CancellationToken ct = default);
```

**After:**

```csharp
Task OnUserCreatedAsync(
    TenantKey tenant,
    UserKey userKey,
    object request,
    UAuthClientProfile clientProfile,
    CancellationToken ct = default);
```

Update custom implementations to accept the additional client profile parameter.

Applications using built-in lifecycle integrations do not need to make this change.

## 4. Identifier and Profile Limits

**Available since preview.2**

The reference Users domain now enforces additional identifier and profile safety limits.

The default maximum is 10 active identifiers per user. Applications requiring a different capacity should configure `Identifiers.Behavior.MaxIdentifiersPerUser`.

Existing profile creation and update operations must also respect the new field-length and metadata limits.

If you use EF Core persistence:

1. Review existing profile data for values exceeding the new limits.
2. Add or apply the appropriate EF Core database migration for your application's DbContext.
3. Verify that applications handling profile validation errors use the returned error codes.

See [Profile Validation & Limits](/docs/plugin-domains/profile-validation-limits) for the supported limits.

## 5. Password Policies and History

**Available since preview.2**

The reference password credential implementation now applies configurable password policies, with Standard as the default level.

Review custom registration, password-change, and password-reset flows to ensure that they handle server-side password validation errors.

Applications using persistent password-history storage must apply the required database migration before enabling password history.

Password history is disabled by default (`RememberLast = 0`).

See [Password Policy & History](/docs/security/password-policy) for configuration and persistence requirements.

## 6. Rate Limiting

**Available since preview.2**

Built-in endpoint rate limiting is enabled by default when using:

```csharp
app.UseUltimateAuthWithAspNetCore();
```

If your application already registers its own rate limiting middleware, avoid installing a duplicate limiter.

To retain application-owned rate limiting:

```csharp
app.UseUltimateAuthWithAspNetCore(useRateLimiting: false);
```

Then configure your existing `UseRateLimiter()` middleware in the appropriate pipeline position.

Applications using `UseUltimateAuth()` without the integrated ASP.NET Core helper do not enable UltimateAuth rate limiting by default.

Review custom HTTP clients and authentication flows for HTTP `429 Too Many Requests` handling.

See [Rate Limiting](/docs/security/rate-limiting) for middleware integration and defaults.
