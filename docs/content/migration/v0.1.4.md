# Migrating to v0.1.4

**Migration Impact: Low**

UltimateAuth v0.1.4 introduces antiforgery protection for cookie-based authentication flows and updates several client and server integration interfaces.

The release strengthens protection against Cross-Site Request Forgery (CSRF) while preserving the standard UltimateAuth developer experience.

**Most applications using the built-in UltimateAuth browser client require no application code changes.** Antiforgery token handling is integrated into the client.

Applications using custom HTTP requests, custom browser bridges, or custom session resolvers should review the changes below.

## 1. Antiforgery Protection for Cookie-Based Authentication

UltimateAuth now validates antiforgery tokens for protected operations when cookie-based authentication is applicable.

This includes relevant authentication operations and authenticated state-changing endpoints.

Requests that fail antiforgery validation are rejected with HTTP `400 Bad Request` and the following error:

```json
{
  "error": "invalid_antiforgery_token"
}
```

### Using the built-in browser client

The UltimateAuth browser client now supports retrieving and submitting antiforgery tokens automatically.

If your application uses the standard UltimateAuth client integration, no additional antiforgery implementation is normally required.

Make sure the server and client packages are updated together.

### Using custom HTTP requests

If your application calls protected UltimateAuth endpoints directly from a browser, you must obtain an antiforgery token and submit it with the request.

The default token endpoint is:

```http
GET /auth/antiforgery/token
```

The response contains:

```json
{
  "requestToken": "...",
  "headerName": "X-UAuth-CSRF",
  "formFieldName": "__RequestVerificationToken"
}
```

The endpoint also issues an antiforgery cookie.

For subsequent protected requests:

1. Obtain a token from the configured antiforgery endpoint.
2. Preserve the associated antiforgery cookie.
3. Send the request token using the returned `headerName`.
4. Include the appropriate authentication credentials for the request.

For example:

```http
POST /auth/logout
X-UAuth-CSRF: <request-token>
Cookie: <authentication-and-antiforgery-cookies>
```

The request token and antiforgery cookie must belong to the same antiforgery context.

**Do not hardcode or fabricate antiforgery tokens.** Always obtain them from the server.

The default endpoint path assumes the standard `/auth` base path. Applications using custom routing or multi-tenancy must use their configured endpoint URL.

### Custom server-side integrations

Applications using custom HTTP clients or server-to-server integrations should review whether their requests use cookie-based authentication.

Antiforgery requirements depend on the authentication transport and operation. They are not automatically equivalent for every bearer-token or header-based request.

Do not disable antiforgery validation to resolve an integration failure. Update the affected request flow instead.

## 2. ISessionIdResolver Is Now Asynchronous

The `ISessionIdResolver` interface has changed to support asynchronous session resolution.

If you implement this interface yourself, update the implementation.

**Before (v0.1.3):**

```csharp
public AuthSessionId? Resolve(HttpContext context)
{
    // Resolve the session identifier.
}
```

**After (v0.1.4):**

```csharp
public ValueTask<AuthSessionId?> ResolveAsync(HttpContext context, CancellationToken ct = default)
{
    ct.ThrowIfCancellationRequested();

    // Resolve the session identifier.
    return ValueTask.FromResult<AuthSessionId?>(null);
}
```

Replace the placeholder return with your existing resolution logic.

If your resolver performs asynchronous operations, use an `async ValueTask<AuthSessionId?>` implementation and await those operations.

Update any direct calls from `Resolve(...)` to `ResolveAsync(...)` and await the result.

Applications using the built-in session resolver do not need to make this change.

## 3. Custom Browser Bridges

The `IBrowserUAuthBridge` interface now includes:

```csharp
ValueTask ConfigureAntiforgeryAsync(string tokenUrl, string? trustedOrigin = null);
```

This allows the UltimateAuth client bootstrapper to configure antiforgery handling for browser requests.

If you provide a custom implementation of `IBrowserUAuthBridge`, implement this new method.

Your implementation must configure the browser-side antiforgery integration using the supplied token endpoint and optional trusted origin.

The exact implementation depends on your browser integration.

**Do not add an empty implementation unless antiforgery handling is already provided by your custom bridge.** Doing so may leave protected browser requests without the required token.

Applications using the built-in UltimateAuth browser bridge do not need to make this change.

## 4. Antiforgery Endpoint Configuration

v0.1.4 introduces a server-side antiforgery configuration section:

```csharp
options.Antiforgery.TokenEndpoint = "/antiforgery/token";
```

The client also exposes the corresponding endpoint setting:

```csharp
options.Endpoints.AntiforgeryToken = "/antiforgery/token";
```

The default endpoint path is `/antiforgery/token`, resolved under the configured UltimateAuth base path.

No configuration change is required when using the defaults.

If you customize the endpoint, ensure the server and client configurations match.

## 5. Verify Your Application

After upgrading to v0.1.4, verify the following flows where applicable:

- Login and logout using the built-in browser client.
- Session refresh and validation.
- Authenticated account and session management operations.
- Custom requests to UltimateAuth endpoints.
- Custom session resolver implementations.
- Custom browser bridge implementations.
- External Hub and multi-tenant configurations.

For applications using custom browser requests, verify that valid antiforgery tokens allow protected operations and missing or invalid tokens are rejected.

## Migration Checklist

- [ ] Update UltimateAuth packages to compatible v0.1.4 versions.
- [ ] Update custom `ISessionIdResolver` implementations, if any.
- [ ] Update custom `IBrowserUAuthBridge` implementations, if any.
- [ ] Add antiforgery token handling to custom browser HTTP requests, if applicable.
- [ ] Verify custom antiforgery endpoint configuration, if applicable.
- [ ] Run authentication, authorization, and session regression tests.

---

**Using the standard UltimateAuth client and built-in session resolution?** No application code changes are normally required. Update your packages and verify your existing authentication flows.
